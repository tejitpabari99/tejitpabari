## Deviations from the PRD/TASKS

1. **Tasks 1–2 pulled forward ahead of phase order, as `sp06-pre`, to unblock SP04.** `src/config/site.ts`
   and `src/components/RouteMeta.tsx` were implemented before SP06 proper started because SP04's
   Tasks 9/10 (`ProjectDetailPage`, `ResearchDetailPage`) import `RouteMeta` directly, per this
   PRD's binding to the `{ title, description, path, image? }` signature — without pulling these
   two files forward, SP04's detail pages could not typecheck. See SP04's
   `code-2026-08-31-0700.md` Deviation 1 for the same event from the other side.
2. **`satori@^0.19.4`, as written in the PRD, does not exist on npm.** `^0.19.3` was installed
   instead (Task 4, `f16075d`) — the nearest published version satisfying the same feature
   requirements; verified against the npm registry at implementation time.
3. **Task 7's scaffolding HTML comment moved from before the frontmatter to just after it.**
   `sample-project.md`'s verbatim PRD/TASKS snippet put the comment above the `---` fence;
   `gray-matter` requires `---` to be the file's literal first bytes, so a leading comment made
   it parse the whole file as body with empty frontmatter, failing
   `assertSlugMatchesFilename`. Confirmed empirically before moving the comment (`194e4df`).
4. **Task 8's top-of-file comment in `sample-project.tsx` was reworded**, not just relocated.
   The verbatim snippet's comment text used literal `<input>`/`<textarea>` tag syntax to describe
   what the component avoids, which tripped `check-no-forms.sh`'s own naive grep (a comment,
   not real markup, still matched the pre-fix pattern). Reworded to avoid spelling the literal
   tag syntax, without changing intent — verified the original wording fails the check and the
   reworded version passes (`aa3a269`).
5. **Two Task 18 snippet assertions were adjusted from TASKS.md's literal text.** The literal
   `getByRole('status', { hidden: true })` snippet assumes `SampleProjectLive`'s ticking `<p>`
   carries an implicit ARIA `status` role from `aria-live="polite"` alone — it doesn't (only
   elements like `<output>`, or an explicit `role` attribute, grant that), and the query throws
   rather than returning null, so TASKS.md's own `?? document.body.textContent` fallback never
   engages. The shipped test instead selects the ticking node via `container.querySelector('[aria-live="polite"]')`,
   a selector unique to that one `<p>` in the component's tree. Separately, `screen.getByText`
   was avoided in favor of the same scoped selector because the page's static caption paragraph
   also contains matching text (an em dash and digits), producing a "multiple elements found"
   error. Both adjustments verified empirically against the real component (`b4d0672`).
