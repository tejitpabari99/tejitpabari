2. **`FirebaseExtended/action-hosting-deploy@v0` is pinned to a floating major tag, not a SHA** — and it is the one step in either workflow that receives the deploy credential (`actions/checkout@v4` and `actions/setup-node@v4`, by contrast, never see a secret). Practical risk is low: it's a Google-maintained action, and a floating-major pin is exactly what `firebase init hosting:github` itself produces when scaffolding this same integration interactively. Noted here specifically because this is the one place in either workflow where the tag-vs-SHA supply-chain distinction is materially meaningful — a compromised or force-pushed `v0` tag would run with deploy credentials, whereas the same compromise against `actions/checkout@v4` or `actions/setup-node@v4` would not reach any secret.
