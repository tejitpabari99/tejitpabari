## Notes (non-blocking)

- [Architect & Regression] `src/pages/PrivacyPage.tsx:39-42` (`ConsentStatus`'s `justCleared` reset
  effect) — the commit message for b89234d justifies the added
  `eslint-disable-next-line react-hooks/set-state-in-effect` by calling it "the identical pattern
  already used in `ConsentContext.tsx`'s own mount effect." It is not identical. `ConsentContext.tsx`'s
  suppressed effect runs once on mount (`[]` deps) to adopt an external source (localStorage) after
  first paint, for SSR/hydration-mismatch safety — a shape React's own guidance accepts needs an
  effect. `ConsentStatus`'s effect has `[consent]` as its dependency and re-runs every time consent
  changes, which is the "reset local state when a prop/related state changes" shape React's guidance
  explicitly says to handle by comparing against a ref during render, not in an effect — the same
  category of fix this round already applied properly elsewhere in the codebase
  (`src/hooks/useCollectionFilter.ts:60-70`, wrapped in `startTransition` instead of suppressed).
  That said, traced through: the suppression causes no real bug. It cannot loop (the effect never
  writes to its own dependency, `consent`), and its only observable cost is one extra render pass when
  a fresh Accept/Decline follows a Clear, silently hiding the stale "Cleared." confirmation a frame
  later — imperceptible, not a correctness or data-loss issue. Verdict: the precedent cited is
  inaccurate, but the suppression itself is harmless, not a hidden bug. Not blocking.

## Verification detail (Privacy & Correctness)

- `disableGa()` (`src/lib/analytics.ts:106-112`) does three things synchronously, in order:
  `gaEnabled = false`, sets `window['ga-disable-G-…']= true` (gtag.js's own documented opt-out flag,
  also respected by GA4 Enhanced Measurement's own auto-fired events, not just this app's manual
  calls), and sweeps cookies. Every call site that can send a hit — `trackEvent`, `trackPageView`
  (both `analytics.ts:115,140`), and `AnalyticsListener.tsx:14` — guards on `gaEnabled`/`isGaLoaded()`
  before touching `window.gtag`. No module-scope `window`/`document` access exists anywhere in the
  five owned files (confirmed by grep); all such access is inside functions, safe for the
  vite-react-ssg build-time prerender.
- Re-grant path (`loadGa()` after `disableGa()`): clears the opt-out flag, sets `gaEnabled = true`,
  and returns early on `gaScriptInjected` — no double `<script>` injection, no stuck state. Verified
  by a real (non-mocked) unit test and confirmed by reading the code.
- Cookie deletion (`deleteGaCookies()`, `analytics.ts:66-85`) sweeps `_ga`/`_gid`/`_gat`-prefixed names
  (covers GA4's `_ga_<container-id>` session cookie via prefix match) across three domain variants
  (host-only, exact hostname, registrable-domain). Checked against the real deployment: the repo's
  `firebase.json` CSP references `tejitpabari.com` as the real custom domain, which is a two-label
  host, so `registrableDomain` correctly resolves to `.tejitpabari.com` — the same scope GA itself
  would use. No cookie should survive a clear on the real domain. (On a bare `*.web.app`/`*.firebaseapp.com`
  preview host, `web.app`/`firebaseapp.com` are public suffixes; neither GA nor this code can set a
  domain-scoped cookie there, so both fall back to host-only cookies, which the `undefined`-domain
  branch already covers — no gap.)
- Task 6 gating (`ConsentStatus`, `PrivacyPage.tsx:31-77`): button renders only when
  `consent !== 'unset'`; the "nothing to clear" status text and click confirmation (`role="status"`,
  "Cleared. …") are both real, asserted by a passing end-to-end test that renders the real
  `PrivacyPage` + `ConsentProvider` + `ConsentBanner` (no mocks) and asserts `localStorage` cleared,
  `document.cookie` free of `_ga=`, the `ga-disable-` flag set, the button gone, and the confirmation
  visible — all from one real click (`src/context/ConsentContext.test.tsx`, last test).
